# Design: a voice-driven personal memory assistant (working name "Stash")

Written 2026-11-10. Nothing here has been run on a phone yet. Every claim about Android, Samsung or Motorola behaviour carries a confidence mark and a way to check it; the checks are the spikes in [RISKS.md](RISKS.md). Results go in [EXPERIMENT_LOG.md](EXPERIMENT_LOG.md).

**Confidence marks:** **[high]** documented by Google/Samsung/Motorola and read for this design · **[medium]** consistent with documentation or widely reported, not confirmed for these exact phones · **[low]** inferred, conflicting reports, or could not be verified.

## 1. Goals and non-goals

### Goals

1. One action from a locked phone starts a voice note; the rest is hands-free and eyes-free (a tone at start, a tone at save).
2. A note becomes data: text, time, location, kind, item, where, person, dates, expiry.
3. Questions by voice or text get a short answer that says when the note was made and whether it is probably stale.
4. Place reminders fire on arrival and stop when done or expired.
5. Everything lives on the phone, encrypted. No server of ours. Backups are encrypted before they leave the app.
6. Speech to text runs on the phone. A hosted language model is optional, cheap, swappable, and sees only note text.
7. Adding is allowed while locked; reading needs the user's biometric or device credential.
8. The owner's parents can use it without help after setup.

### Non-goals

- Not a general assistant, journal, to-do manager or calendar. It answers "where is it, who has it, what did I need here".
- No always-listening microphone and no wake word (section 6 explains why).
- No tracking of objects (no Bluetooth tags). It remembers what the user said.
- No sharing between people in version 1, no accounts, no sync between a person's devices.
- No speaker verification as security.
- Not a Play Store product for the public.

## 2. Threat model

What is being protected: a record of where valuables are, who has borrowed what, where the user goes, and whatever else gets said to it. A burglar's shopping list if leaked.

| Threat | In scope? | Defence |
| --- | --- | --- |
| Someone picks up the phone (family, guest, thief) while it is locked | Yes, primary | Reading and asking need device unlock plus the app's own gate. Capture screens show only the current note. Reminder notifications hide their text on the lock screen. |
| Someone uses the phone while it is unlocked (handed over to show a photo) | Yes | App gate: biometric or PIN on opening any reading screen, with a short grace period. `FLAG_SECURE` on reading screens (no screenshots, hidden in recents). |
| Lost or stolen phone, powered off or never unlocked | Yes | Android file-based encryption, plus SQLCipher database whose key is wrapped by a hardware-backed Keystore key that cannot leave the device. |
| Other apps on the phone | Yes | App-private storage, no exported components except the trigger entry points, which accept no data. No content provider. |
| The backup target (cloud drive, home server, a synced folder) is read by someone else | Yes | Backup file is encrypted in the app with a key only the user holds (a printed recovery code). The target sees ciphertext and file size and dates. |
| The speech engine or model provider learns too much | Yes | Speech on the phone. Hosted model gets note text only: no location, no time, no identity, no other notes except the few retrieved for a question. Local-only notes are never sent. The model can be switched off entirely. |
| A stolen API key runs up a bill | Yes | One key per person in its own workspace with a small monthly spend cap; the owner can revoke one without touching the others. |
| A person nearby speaks a note into the locked phone (prank, poisoning) | Partly | Low harm. Notes captured while locked are marked and shown in a "check these" list. |
| A recording of the user's voice | Not relevant | Voice is not a credential anywhere in the design. |
| Forensic extraction from a phone that has been unlocked since boot; malware with root; a compromised OS | **No** | Out of scope for version 1. Card 30 (sealed inbox, keys that lock with the screen) narrows the first of these later. |
| The model provider's own retention | Accepted | Anthropic's API does not train on inputs by default and keeps them for a limited time **[medium: check the current commercial terms before relying on it]**. Anyone unhappy with that uses local-only notes or no hosted model. |

Known weak point in version 1: the database key must be usable while the phone is locked, because capture writes while locked. So the "reading needs authentication" rule is enforced by the app's code, not by cryptography. That is enough against a person holding the phone; it is not enough against an attacker who can run code as the app on a locked phone. Card 30 closes this.

## 3. Architecture

One Android app, one module, no backend.

```
 triggers ──► CaptureActivity (shown over the lock screen)
                │  start cue → record (AudioRecord, 16 kHz) → end-of-speech → stop
                ▼
            SpeechToText (on the phone) ──► text
                │                            │ if it fails: keep encrypted audio, retry later
                ▼
            save note (text, time, location, UNSORTED) → save cue
                │
                ▼ (in the background, may be seconds or hours later)
            RulesStructurer (always, offline) ──► fields
            HostedStructurer (optional, if a key is set and the note is not local-only) ──► better fields
                │
                ▼
            domain rules: resolve item/person/place against what is known, supersede, set expiry, create reminder
                │
                ▼
            encrypted database (Room on SQLCipher, FTS5 index)

 ask (voice or text, after unlock + app gate)
   question → local question parser → search (entities + FTS5 + ranking)
            → answer written locally from fields when the question fits a known shape
            → otherwise QuestionAnswerer (hosted, optional) over the top few non-local-only notes
            → shown and spoken (on-device text to speech), always with the note's date

 reminders: geofence broadcast or alarm → notification (text hidden on lock screen) → Done / Later
 backup:    weekly, encrypted in the app → a folder the user picked (any storage provider)
```

Design choices that shape everything:

- **The save tone means "your words are stored".** It plays only after the text (or, if transcription failed, the encrypted audio) is written to disk. Structuring happens afterwards and can fail without losing anything.
- **The app works with no network and no API key.** A rules-based structurer handles the common sentence shapes; answers to "where/who/what at" questions are written from fields by code. The hosted model improves both but is never required. This is what makes it safe to hand to the parents before any key decision is made, and it is the fallback when the model returns nonsense.
- **No long-running service.** Everything runs because the user did something (a trigger), or because the system delivered an event (geofence, alarm, scheduled work). That avoids most battery-manager trouble and all "always listening" concerns.
- **All network code is in one package** (`model.hosted`, later `update`), so the privacy rules can be checked by a test that scans imports.

## 4. Data model

Room entities on a SQLCipher database. IDs are random UUID strings (so backups merge without collisions). Times are UTC epoch milliseconds plus the zone ID at capture.

| Table | Main columns | Notes |
| --- | --- | --- |
| `note` | `id`, `created_at`, `zone`, `raw_text` (as transcribed), `text` (after the user's corrections), `kind`, `status` (`ACTIVE`, `SUPERSEDED`, `DONE`, `EXPIRED`), `local_only`, `captured_locked`, `needs_review`, `lat`, `lon`, `accuracy_m`, `fix_age_s`, `captured_place_id`, `structure_source` (`NONE`, `RULES`, `MODEL`, `USER`), `structure_json`, `structure_confidence`, `stt_engine`, `expires_at`, `done_at`, `superseded_by`, `deleted_at` | The source of truth. Other tables can be rebuilt from `text` + `structure_json`. Deleting is a soft delete for 30 days (undo), then real. |
| `item` | `id`, `name`, `aliases` (JSON list), `volatility` (`DAILY`, `NORMAL`, `STORED`) | "reading glasses" with aliases "glasses", "readers". Volatility sets how fast answers go stale. |
| `placement` | `id`, `item_id`, `note_id`, `where_text`, `place_id`, `copy_label`, `at` | One row per "I put X in Y". The newest per item (per copy label) is current. |
| `person` | `id`, `name`, `aliases` | |
| `loan` | `id`, `note_id`, `item_id`, `person_id`, `direction` (`LENT`, `BORROWED`), `on_date`, `due_date`, `returned_at`, `last_nudge_at` | |
| `place` | `id`, `name`, `aliases` | "Costco", "home", "the cabin" |
| `place_location` | `id`, `place_id`, `lat`, `lon`, `radius_m`, `source` (`HERE`, `SEARCH`, `LEARNED`) | A chain has several. |
| `reminder` | `id`, `note_id`, `text`, `trigger` (`PLACE`, `TIME`, `NONE`), `place_id`, `due_at`, `expires_at`, `state` (`ACTIVE`, `SNOOZED`, `DONE`, `EXPIRED`), `last_notified_at`, `notify_count` | |
| `note_revision` | `id`, `note_id`, `at`, `old_text`, `old_structure_json`, `reason` | History of edits and re-structuring. |
| `pending_audio` | `id`, `note_id`, `file`, `created_at`, `attempts` | Encrypted audio awaiting transcription; row and file deleted on success or after 7 days. |
| `note_fts` | FTS5 over `text`, item names and aliases, person names, place names, `where_text` | Rebuilt from the tables; never backed up. |

Rules (pure Kotlin, unit-tested, card 09):

- **Supersession.** A new `PLACED` note for an item marks that item's previous current placement's note `SUPERSEDED` and sets `superseded_by`. If the note names a copy ("my spare key", "the blue hat"), only the same copy is superseded. A `LOAN` (lent) note also supersedes the item's placement: the guitar is now "with Frank". Marking a loan returned does not restore the old placement; the answer becomes "Frank returned it on …; before that it was in …".
- **Expiry defaults** (all editable per note and per kind in settings):

  | Kind | Default | Why |
  | --- | --- | --- |
  | `PLACED` | never expires; superseded by a newer note | The owner's rule: latest wins, history kept |
  | `LOAN` | never expires; nudge at the due date, or after 30 days if none, then every 60 days | A loan matters until it is returned |
  | `ERRAND` (buy X at Costco) | 45 days; 14 days if the model or rules flag it perishable | "I wouldn't want a reminder six months later" |
  | `REMINDER` with a time | 7 days after it is due | |
  | `REMINDER` without a time | 90 days | |
  | `FACT` | never | "$15.99 on April 3" is reference data |

  Expired notes stop reminding and drop out of "what do I need" answers; they stay searchable as history until the user deletes them.
- **Staleness.** An answer from a `PLACED` note carries a warning when the note is older than: 2 days for `DAILY` items (keys, glasses, wallet), 90 days for `NORMAL`, 365 days for `STORED` (the Christmas tree stand). Wording: "Nightstand drawer. You told me on 12 March, eight months ago, so it may have moved."
- **Disagreement.** If two active notes about an item conflict (different copies not distinguished, or a correction that did not supersede), the answer gives the newest first and mentions the other: "Most recently the hall closet (3 days ago). Before that you said the garage (2 weeks ago)."

**Migrations.** Room schema export checked into the repository; every schema change ships a migration and a migration test from each earlier version. `structure_json` carries its own `v` so stored structures can be re-read or re-derived after the schema of the structurer changes.

**What the encrypted backup contains.** A JSON export of every table except `note_fts` and `pending_audio`, the settings (not the API key, not the database key), the schema version, and any attached photos. Restoring is an import through the same code as migration, so a backup from an older version restores into a newer app. Section 9 covers format and keys.

## 6. Trigger strategy

### Plan

1. **Spike 01** builds a throwaway app with every row above and a checklist. It decides, per phone, which trigger is primary. Nothing else in the build depends on which one wins, only on at least one passing, and the notification action is expected to pass everywhere.
2. Expected outcome (to be confirmed): owner uses the **assistant role on the side key long-press** (or double-press if it passes locked); wife uses the **assistant role or the external-display widget**; parents use the **cover-screen widget and the notification action**, keeping Gemini on their long-press unless they prefer otherwise.
3. Every phone also gets the tile, the home widget and the launcher shortcut, because they are nearly free.

### Hands-free finish

Recording stops by end-of-speech detection: speech must start within 6 seconds (else cancel with the failure tone), stops after 1.8 seconds of silence once speech has been heard, hard limit 45 seconds. A large Stop button and a Cancel button are on screen for anyone looking. After save, the screen shows the transcript for 8 seconds with an Undo button, then closes and the phone goes back to locked. Optional setting, on by default for the parents: speak a short confirmation ("Saved: reading glasses, nightstand drawer").

## 7. Speech and model interfaces

### Speech to text

```kotlin
interface SpeechToText {
    /** True if this engine can run now with no network. */
    suspend fun isReady(): Boolean
    /** 16 kHz mono PCM in, text out. Must not touch the network. */
    suspend fun transcribe(pcm: ShortArray, languageTag: String): Transcript
}
data class Transcript(val text: String, val confidence: Float?, val engine: String)
```

The app records the audio itself (so it controls the cues, end-of-speech, and can keep the audio for a retry) and hands a finished buffer to the engine. Two candidate engines, decided by **spike 03**:

| Engine | For | Against |
| --- | --- | --- |
| **Bundled model via sherpa-onnx** (Apache-2.0; ONNX Runtime; Whisper, Moonshine or Parakeet models; includes a voice-activity detector) | Same behaviour on all three phones; no dependence on which Google/Samsung speech components are installed; works on recorded buffers; never has network access | Native library plus a model: roughly 100 MB (Whisper tiny/Moonshine tiny) to 650 MB (Parakeet 0.6B) on disk per a third-party benchmark **[medium; sizes to be measured]**; a second or more of compute per note |
| **Android's on-device recognizer** (`SpeechRecognizer.createOnDeviceSpeechRecognizer`) | No extra download, fast, maintained by the platform | Availability and quality differ by manufacturer and language pack; it records for itself, so no stored audio for retry and less control over cues; must be called from the main thread with its own lifecycle; on Samsung the provider may be Samsung's or Google's **[low]** |

Recommendation going in: **the bundled engine is the default, the platform recognizer is the fallback implementation**, because predictability across three households matters more than APK size for a sideloaded app. Spike 03 can overturn this. Google's ML Kit GenAI speech API was also looked at: it is in alpha, and its better mode is Pixel-only today, so it is not a candidate.

No cloud speech fallback is planned. If on-device accuracy turns out to be poor for a particular person, the fix is a larger model on that phone, then the correction screen, before any cloud option.

Raw audio is deleted as soon as its text is saved. The only audio kept is for notes whose transcription failed, encrypted, for up to 7 days of retries.

**Names are the weak spot** ("Frank" or "Frankie", "frunk", "Costco"). Defences, all local: after structuring, extracted item, person and place names are fuzzy-matched (edit distance and sound-alike) against the names already known; a near-miss is offered as "Did you mean Frank?" in the review list, never silently merged; a correction teaches an alias.

### Language model

```kotlin
interface NoteStructurer {
    /** Text in, fields out. The implementation receives nothing but the text. */
    suspend fun structure(text: String): StructureResult
}
interface QuestionAnswerer {
    /** The question and a few notes' text with their dates rendered as words. Nothing else. */
    suspend fun answer(question: String, notes: List<AnswerNote>): AnswerResult
}
sealed interface StructureResult { data class Ok(val fields: NoteFields, val source: String) ; data class Failed(val reason: String) }
```

Implementations:

- `RulesStructurer` (offline, always available): pattern rules for the common shapes ("I'm putting X in Y", "I put X in/on/under Y", "X is in Y", "I loaned/lent X to P [on date]", "I borrowed X from P", "buy/get/pick up X at/when I'm at P", "remind me to X [by/on date]"). Anything else becomes `FACT`.
- `HostedStructurer` / `HostedAnswerer` (optional): a Haiku-class hosted model. First provider is Anthropic (`claude-haiku-5-5`) through the official Java SDK, using structured outputs so the reply is schema-valid JSON.
- Later, if wanted: an on-phone model (Gemini Nano through ML Kit's Prompt API; device lists seen for this research include the razr ultra 2025 and Galaxy S26 but not clearly the S25 Edge or Flip 7 **[low]**), or another provider. Each is one new class behind the same two interfaces.

**What the hosted model is sent**, and nothing more:

- Structuring: a fixed instruction, the JSON schema, and the note's text.
- Answering: a fixed instruction, the question, and at most 6 retrieved notes, each as its text plus its age in words ("8 months ago"). No coordinates, no place names the user did not say, no clock time.

**Dates without sending the date.** The model is not told today's date. It returns date expressions as data ("month 1, day 5, no year", "in 2 weeks", "next Friday") and the app resolves them locally: an event date ("loaned on Jan 5th") resolves to the most recent such date not in the future; a due date resolves to the next one.

**Local-only notes** never reach the hosted model. A note becomes local-only when: the user starts with a marker phrase ("private note …"); a local keyword check fires (password, PIN, passcode, combination, social security, account number, "the code is"); the user toggles it; or the whole app is in "never use a hosted model" mode. The check runs before any network call and is unit-tested with a fake transport that fails the test if called.

**When the model misbehaves.** Schema-invalid output, a refusal, a timeout, or fields that contradict the text (an item name that does not appear in the note) → keep the rules result, mark the note "needs review", never block the save. Low confidence is shown to the user as "I'm not sure I understood this one" in the review list, not hidden.

## 8. Search and answering

Three ways to find a note, and why they are combined in this order:

| Method | Privacy | Cost | Speed offline | Weakness |
| --- | --- | --- | --- | --- |
| **Structured lookup** (item → current placement; person → loans; place → errands) | Local | Free | Instant | Needs structuring to have worked |
| **Keyword search** (SQLite FTS5 with stemming, over text plus item aliases) | Local | Free | Instant | Misses synonyms the note never used ("specs" for "glasses") |
| **Semantic search** (embeddings) | Local if the embedding model is on the phone; otherwise every note's text goes to a provider | An on-phone model is another 25–200 MB and native code; a hosted one costs per note and breaks local-only | Fast enough for a few thousand notes by brute force | Size and complexity for a small gain at this scale |
| **Ask a model over retrieved notes** | The question and a handful of notes leave the phone | About $0.0002 per question | Not available offline | Can invent; must be given dates; must be told to say "I don't know" |

Design:

1. Parse the question locally into a shape: `WHERE_IS(item)`, `WHO_HAS(item)`, `WHAT_DID_I_LEND(person)`, `WHAT_AT(place)` (also "what do I need here" using the current location), `WHEN/WHAT` free-form.
2. Retrieve: entity lookup by name and alias with fuzzy matching, plus FTS5. Rank by text match, then prefer `ACTIVE` over `SUPERSEDED`/`EXPIRED`, then recency.
3. If the shape is one of the first four and a structured match exists, **write the answer in code** from the fields. No model call, works offline, cannot invent anything.
4. Otherwise, if a hosted model is enabled, send the question and the top notes that are not local-only. If the best match is local-only, answer from it locally ("Your most relevant note is private: '…'").
5. Otherwise show the top matching notes as a list.
6. Every answer names its note's date. Every answer from a stale note says so. No match → "I don't have a note about that", plus the closest near-misses if any.

**The cheap substitute for semantic search:** when a note is structured, the structurer also returns a few aliases for the item ("reading glasses" → "glasses", "readers", "specs"). They go into the FTS index. That recovers most synonym misses for no extra model, no extra download, and nothing extra sent. An on-phone embedding index is in FEATURES.md as "later", to be added only if real use shows misses.

**Place-aware reminders with minimum location access.**

- *Without* "allow all the time": whenever the app is opened or a note is captured, the one location fix it takes anyway is compared with the places that have active errands, and a card says "You're at Costco: ground beef, AA batteries". "What do I need here?" does the same on request. This needs only while-in-use location.
- *With* "allow all the time" (opt-in, asked at the first place reminder): Play services geofences, registered only for places that currently have an active errand and removed when the last one is done or expires. Radius at least 150 m; arrival notification at most once per place per 4 hours; re-registered after reboot and app update and checked daily, because geofences are dropped silently in those cases **[high]**.
- A place gets a map location by "I'm here now" (no network), or by remembering where an errand was marked done, or by an address search using Android's geocoder, which sends the search text to the phone's geocoding provider (Google) and is labelled as such.
- A place name is attached to a captured note by comparing its coordinates with the user's saved places, on the phone. No reverse geocoding.

## 9. Privacy and security model

- **Database:** SQLCipher (AES-256) under Room. The 256-bit database key is random, generated on first run, and stored only as ciphertext wrapped by an AES-GCM key in the Android Keystore (StrongBox if available). The key cannot be exported, so the database file is useless off the phone.
- **Android's own cloud backup and device-to-device transfer are disabled** for the app (they would copy a database the new phone cannot open, and would put it in Google's cloud).
- **App gate:** `BiometricPrompt` with strong biometrics or device credential before any screen that shows stored notes; grace period 2 minutes by default (setting: "ask every time" / "2 minutes" / "trust the unlocked phone", the last intended for the parents if the owner chooses). Reading screens use `FLAG_SECURE`.
- **Asking from the lock screen** dismisses the keyguard first (fingerprint or PIN), then listens. There is no path that speaks or shows a stored note on a locked phone.
- **Notifications:** reminder text is hidden on the lock screen by default ("A reminder for Costco. Unlock to see"); a setting allows showing it.
- **Encrypted backup:** made in the app with a random 256-bit backup key, shown once as a recovery code (QR and grouped characters) to print or put in a password manager. File = small header + streaming authenticated encryption (Tink AES-256-GCM-HKDF streaming) of a zip holding the JSON export and photos. Written through Android's Storage Access Framework to a folder the user picks: a local folder that Syncthing-Fork replicates to the home server, a cloud drive, or anything else with a storage provider. The app needs no network permission for backup. Weekly and after every 25 new notes, keeping the last 5 files.
- **Lost or replaced phone:** install, scan the recovery code, pick the newest backup file. Without the recovery code a backup cannot be opened by anyone; onboarding says this plainly and offers a test restore.
- **API key:** stored encrypted under a Keystore key, never in backups, never logged. Entered by scanning a QR code the owner generates (so the parents never type it).
- **Voice-print:** not built. No Android API, defeated by a recording, and a cold locks the owner out. As a convenience layer it would add a native model and enrolment for a benefit the fingerprint already gives.
- **Raw audio:** not kept (section 7).
- **Logging:** no note text, coordinates or keys in Logcat in release builds; a debug build may log them.

## 12. Installing and updating in three households

The owner assumed sideloading. Two findings push against using it for the family phones:

- Samsung **Auto Blocker** (on by default) refuses installs from outside the Play and Galaxy stores **[high]**. Every update on the parents' Flip 7 would mean turning it off, installing, and turning it back on.
- Google's **developer verification** will, from 2027 in most countries, require the developer of a sideloaded app to be registered **[medium]**.

Options:

| Method | For | Against |
| --- | --- | --- |
| `adb install` from Android Studio | Works for the owner's phone under every rule | Needs a cable or wireless debugging at each phone |
| Signed APK on a private page (GitHub Releases) with an in-app "update available" check and the system installer | No Google account involvement; owner controls everything | Auto Blocker on the Samsungs; "install unknown apps" permission; a tap-through per update; affected by developer verification later |
| **Google Play internal testing** (up to 100 invited testers, not public, not listed) | Updates arrive automatically like any app; Auto Blocker and developer verification are non-issues; nothing for the parents to do | $25 once and identity verification for a Play developer account; the APK passes through Google (the code, not the data); Play policies on background location and the assistant role could in principle be raised even for a private track **[low risk for internal testing]** |
| Obtainium (open-source updater app) | No Play account | One more app on the parents' phone; still a manual tap; still Auto Blocker |

**Recommendation:** develop and run on the owner's phone with `adb`. Before the app goes onto the other two phones, run **spike 06** and, unless it shows a problem, use **Play internal testing** for the family. If the owner prefers to stay off Play, the fallback is GitHub Releases plus the in-app check, with a free limited-distribution developer registration before 2027. The decision is Q4 in QUESTIONS.md. Either way the release build is signed with one key kept outside the repository and backed up; losing it means every phone must uninstall and restore from backup.

## 13. Failure modes

| Failure | What the user experiences | Design response |
| --- | --- | --- |
| Transcription gets a name wrong ("Frankie") | A wrong name in a note | Fuzzy match against known names; "Did you mean Frank?" in the review list; correction teaches an alias; raw text is always kept |
| Transcription fails or the engine is not ready | Different (single low) tone then the save tone | Encrypted audio kept, retried in the background for 7 days; the note appears as "Recording waiting to be understood" |
| Nothing was said, or noise | Failure tone, nothing saved | Speech must start within 6 seconds |
| No GPS indoors | Nothing visible | Take the best fix within 5 seconds, else the last known fix with its age, else none. Accuracy and age are stored, and location is never required. Place name comes from saved places only when within their radius |
| No network | Nothing visible at capture | Capture, rules structuring, structured answers and search are all offline. Model structuring is queued until there is a network |
| Model returns nonsense, refuses or times out | Possibly a note in "check these" | Keep the rules result; validate model output against the text; never overwrite a user correction |
| The user forgets a reminder exists | A reminder that never fires | Weekly digest lists active reminders and loans; "expiring soon" line; the home screen shows counts |
| Battery manager kills the app | Missed place reminder | No service to kill. Geofences and alarms are delivered by the system; onboarding sets "never sleeping" when place reminders are on; a daily check re-registers geofences; the opportunistic "you're at Costco" card catches what the geofence missed |
| The phone reboots | Missed place reminder | Re-register geofences and alarms at boot and after update |
| Two notes disagree | A confusing answer | Newest first, the other mentioned with its date; one tap to say which is right |
| "My keys" could be several things | A wrong or partial answer | List up to three candidates with dates; offer to name the copies |
| The user says a correction as a new note ("actually it's in the garage") | Two notes | The rules and model treat "actually/I moved" as `PLACED` for the item most recently mentioned; it supersedes |
| A reminder fires at the wrong branch or while driving past | An unwanted notification | Arrival needs 3 minutes of dwell where the phone supports it; once per 4 hours per place; "not now" snoozes until the next visit |
| Too many notifications | The user turns them off | Budget: at most 3 proactive notifications a day outside arrivals; nudges are batched into the digest; quiet hours 21:00–08:00 |
| The assistant role is lost after an update | The long-press does nothing or opens Gemini | The app checks at each start whether it still holds the role and shows a one-tap fix; the notification action still works |
| Phone lost | Everything on it gone | Encrypted backup + recovery code; revoke that person's API key |
| Recovery code lost | Backups cannot be opened | Stated at onboarding; a new code can be made at any time from the working phone, which re-keys future backups |
