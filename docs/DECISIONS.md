# Decisions

Choices made in this design and the alternatives rejected, so they are not argued again without new information. A spike result in [EXPERIMENT_LOG.md](EXPERIMENT_LOG.md) is new information; when one overturns a decision, edit the entry here and say why.

| # | Decision | Alternatives rejected | Why |
| --- | --- | --- | --- |
| D1 | **Build a new app** rather than adopt or fork an existing one | Memora, Dozy, Memex, Mycelia, Echo-named projects, Google's Find Hub "Remembered" | Closed ones cannot gain custom triggers or a swappable model; open ones are journals or servers in other stacks with no locked-phone capture, place reminders or expiry. Details in DESIGN.md §14. |
| D2 | **Capture is an activity shown over the lock screen**; triggers only launch it (or its service) | A background service started by a trigger; a permanently running listener | Android permits the microphone from a visible activity, a widget tap, a notification action or the assistant service, and from little else. A visible screen also gives Stop, Cancel and Undo. |
| D3 | **No always-on anything**: no wake word, no shake detector, no permanent service | Shake/chop via accelerometer service; software hotword | Platform rules block opening the microphone from such a service; battery managers kill them; false triggers; and it is the opposite of the privacy promise. |
| D4 | **Triggers are decided by measurement** (spike 01), with the notification action as the assumed universal fallback and the assistant role as the best one-button option | Committing now to Samsung side-key double-press, back-tap or a headset media key | Nobody documents what works from a locked One UI 8/9 or Motorola phone. The capture screen does not care which trigger wins. |
| D5 | **The assistant role is optional and per person** | Requiring it; ignoring it | It is the only documented one-press hardware route with a microphone exemption, but it displaces Gemini. That is each person's call (Q1). |
| D6 | **The save tone means the words are on disk**, not that they were understood | Tone at end of recording; tone after structuring | The user's only question at that moment is "did it take?". Understanding can be fixed later; a lost note cannot. |
| D7 | **[Superseded by D46, 2026-11-11]** **The app records the audio itself** and hands a buffer to the speech engine | Letting Android's recognizer own the microphone | Control over cues and end-of-speech, the same behaviour on three phones, and the ability to keep encrypted audio for a retry when transcription fails. Revisit only if spike 03 shows the platform recognizer is clearly more accurate. |
| D8 | **[Superseded by D46, 2026-11-11; "no cloud speech" still stands]** **Bundled on-device speech (sherpa-onnx) by default**; platform recognizer as the alternative; **no cloud speech** | Cloud speech as default or automatic fallback; ML Kit GenAI speech (alpha, best mode Pixel-only) | Must-have 7. Predictability across manufacturers outweighs APK size for a sideloaded app. Spike 03 can overturn the default. |
| D9 | **[Amended by D46: no audio is stored at all, not even pending]** **Raw audio is deleted once transcribed**; kept encrypted only while transcription is pending (up to 7 days) | Keeping audio for playback or re-transcription | Audio is the most sensitive form of the data and the largest. The text plus the correction screen is enough. |
| D10 | **[Amended by D43: the rules are now the floor, the model the main path; the app still works without it]** **A rules-based structurer always runs first; the hosted model is an optional upgrade** | Model-only structuring | The app must work offline, with no key, for private notes, and when the model fails. It also makes the parents' set-up independent of the key question. |
| D11 | **[Amended by D43: coded answers stay; free-form questions use a bounded tool loop]** **Common questions are answered by code from structured fields**; the model answers only free-form questions over a few retrieved notes | Sending every question to a model | Offline, instant, free, and cannot invent a location. |
| D12 | **The hosted model receives only text** and returns date *expressions*; the phone resolves them | Sending today's date for relative dates; sending place or time context | Keeps "time and location never leave the phone" literally true at the cost of a small resolver. |
| D13 | **[Amended by D68: "local-only" is now the one Private mark, with wider effect; the decide-on-the-phone rule stands]** **Local-only is decided on the phone before any call**: marker phrase, keyword detector, per-note switch, global switch | Asking the model whether a note is sensitive | By the time a model could say so, it has been sent. |
| D14 | **[Amended by D50: FTS4 through Room; embeddings still later]** **Search = entity lookup + SQLite FTS5 + model-supplied aliases**; no embeddings in version 1 | On-phone embedding index; hosted embeddings; a vector database extension | At a few thousand short notes, names and aliases find things. Embeddings add a second model and native code for a small gain; hosted embeddings break local-only. Listed as "later". |
| D15 | **[Amended by D58: the choice stands; it is applied with the release build, after a spike, not second in the order]** **Room on SQLCipher**, database key random and wrapped by a hardware-backed Keystore key | Jetpack Security's EncryptedFile around a plain database; field-level encryption; Realm/ObjectBox | Whole-database encryption with a mature library, full SQL and FTS5, and Room's migration testing. |
| D16 | **Version 1 enforces the reading gate in code**; the key works while locked. Cryptographic enforcement is a later card (30, sealed inbox) | Building the sealed inbox first; binding the key to biometrics from the start | Capture must write while locked. The sealed inbox touches every background path and would slow the first usable version; the version-1 threat is a person holding the phone. The limit is stated openly (RISKS.md R8). |
| D17 | **App gate with a short grace period** on top of the device lock, `FLAG_SECURE` on reading screens | Relying on the device lock alone; prompting on every screen | Covers the "unlocked phone handed to someone" case without making the owner's own use tedious. Grace is a setting (Q5). |
| D18 | **Voice-print is not built** | Speaker verification as a convenience layer | No platform API, spoofable, fails with a cold, needs enrolment and another model, and adds nothing the fingerprint does not. |
| D19 | **Android's own backup is disabled; the app writes its own encrypted backup** through the system folder picker, keyed by a printed recovery code | Android Auto Backup; passphrase-derived key; direct upload to Home Assistant, WebDAV or a cloud API | The database key cannot leave the phone, so a system backup would be unreadable. A random key avoids weak passphrases and a key-stretching dependency. The folder picker lets Syncthing, a cloud drive or a NAS app do the transport with no network code in this app. A direct Home Assistant target can be added later if wanted (Q7). |
| D20 | **Backups are a JSON export inside an encrypted container**, restored by import | Copying the SQLCipher file | Restores across schema versions and onto a phone with a different database key. |
| D21 | **Geofences only on opt-in and only for places with something pending**; an opportunistic "you're here" check needs no background location | Always-on background location; polling location on a timer; no place reminders | Minimises "allow all the time". The opportunistic mode is the fallback if spike 05 fails. |
| D22 | **No reverse geocoding.** Place names come from places the user named, matched on the phone | Android Geocoder or a web service to label every note | Reverse geocoding sends coordinates off the phone for a label the user rarely needs. Address *search* when creating a place is allowed, explicit and labelled. |
| D23 | **Google Play services for location and geofences** | Platform `LocationManager` proximity alerts; a self-built geofence loop | Play services geofencing is the only approach with acceptable battery use and reliability, and is present on all three phones. |
| D24 | **[Superseded by D48: tighter budget, digest first]** **Notification budget** (3 a day outside arrivals, quiet hours, weekly digest instead of many nudges) | Notifying whenever something is due or stale | The app survives only if it is not annoying. |
| D25 | **Reminder text is hidden on the lock screen by default** | Showing it | Otherwise notifications bypass the locked-phone policy. A setting allows it. |
| D26 | **[Amended by D44: same model, no SDK, one extractor interface]** **Anthropic `claude-haiku-5-5` first, through the official Java SDK, behind `NoteStructurer`/`QuestionAnswerer`** | A provider-neutral framework; an on-phone LLM first; OpenAI-compatible shims | Cheapest capable hosted option at the time of writing; the owner already uses Claude; two small interfaces are all the abstraction needed. An on-phone model is one more implementation later. |
| D27 | **[Deferred with the family rollout; one key for now, Q17]** **One Anthropic organisation, one workspace and key per person, each with a small spend cap** (recommended; owner decides, Q3) | One shared key; each household opens its own account; a proxy on the owner's Home Assistant | One bill, per-person revocation, capped loss if a phone is stolen, nothing for the parents to manage, no server of ours. |
| D28 | **minSdk 35, target 37, arm64 only** | Supporting older Android; 32-bit | The oldest phone is a 2025 flagship. A high floor removes branches and keeps native libraries small. |
| D29 | **Single module, no dependency-injection framework, no multi-agent or LLM orchestration library** | Hilt; multi-module; LangChain-style libraries | The app is small. Each addition is something the cheaper builder model can get wrong. |
| D30 | **Widgets, tiles and notifications never show note content** | A "recent notes" widget | They render outside the app lock. |
| D31 | **Family distribution through Google Play internal testing is recommended; sideload with an in-app update check is the fallback** (owner decides, Q4) | Sideload only; Obtainium | Samsung Auto Blocker and Google's coming developer verification make sideloading a recurring chore on the parents' phone. This challenges the brief's sideloading assumption for the family phones only; the owner's own phone stays on `adb`. |
| D32 | **Everything a spike learns is written in EXPERIMENT_LOG.md and cards read it before building** | Encoding expected phone behaviour in the cards | The cards were written before any phone was tested. The log is the truth. |
| D33 | **Each person's data stays on that person's phone; no sharing in version 1** | Household shared lists; a family server | The brief's default. Sharing needs a transport and a trust model; see Q8 for a minimal later option. |
| D34 | **Phase 1 is the owner's own phone only; family distribution is deferred (2026-11-11)** | Setting up Play internal testing now | The owner wants to prove the idea locally before any spend or any other person's phone is involved. No Play developer account, no sideload-update machinery, no family testing until then. D31 stands as the recommendation for when the family is involved. |

## Revision 1 (2026-11-11): from "where did I put it" to "capture anything, find it later"

Appended, not rewritten. Rows above marked **[Superseded]**, **[Amended]** or **[Deferred]** keep their original text; the reason is in the row named. Decisions not marked still stand. D4, D5, D21–D23, D31 and D33 stand but apply to work that is deferred.

| # | Decision | Alternatives rejected | Why |
| --- | --- | --- | --- |
| D35 | **The app is a capture-anything inbox**: places, loans, tasks, readings, events, reference facts, ideas. The non-goal "not a to-do manager or journal" is withdrawn. It is still not a calendar, project manager, chat assistant, adviser, or anything that listens unprompted (DESIGN.md §1) | Keeping the narrow scope; becoming a general assistant | The owner's stated use: speak almost anything, submit, move on. The first real note was already outside the old scope. |
| D36 | **The raw words are the source of truth, kept for good; everything the model produces is a disposable second layer** that can be rebuilt. The owner's own actions (done, snooze, edit, merge) are also truth, and "pin" the records they touch | The model's structured output as the only copy; a model-maintained database; storing only a cleaned-up rewrite | Nobody reviews the filing, the model will sometimes be wrong, and models improve. A wrong guess must cost a re-read, never a memory. |
| D37 | **One capture can produce several records**, at most 8, each carrying the exact quote it came from; measurements taken together are one record | One record per capture (the prototype); unlimited splitting | People say several things in a breath. The quote and the cap make over-splitting detectable and reversible. |
| D38 | **Eight fixed kinds** (`PLACED`, `LOAN`, `TASK`, `READING`, `EVENT`, `REFERENCE`, `IDEA`, `OTHER`) plus free-form tags and aliases | Free-form types invented by the model; the brief's six without `EVENT`; many fine-grained kinds | Code must act differently on a task, a reading and a placement, so those must be fixed. `EVENT` answers "when did I last…" and is how tasks get closed by speaking. Confusion among the search-only kinds is harmless. |
| D39 | **One `subject` table** for items, people, places and things notes are about ("pool", "car"); names resolved by code, near-misses flagged, never merged silently | Separate item, person and place tables (first design); letting the model assign IDs | One resolver, one merge action, and a "tell me about the car" page for free. |
| D40 | **Readings are stored one value per row** (metric, value as said, number, unit, time, subject); units are never invented; values are never corrected or interpreted | Readings as free text; a JSON blob per note; target ranges and advice | "Last value" and trends are queries. Advice is a liability the app cannot stand behind. |
| D41 | **Task lifecycle: open, snoozed, done, expired, dropped.** A spoken report closes a task automatically only when the model is confident and named the task; otherwise the app asks once in the attention list | Always automatic; never automatic | A wrong close is silent and worse than a missed one; but he reports by talking, so the common case must just work. |
| D42 | **Due hints come back from the model as expressions and are resolved on the phone; reminder schedules are plain code** | Telling the model the date; letting the model propose reminder times | Keeps the date on the phone (D12 stands) and makes scheduling testable with a fixed clock. |
| D43 | **[Amended by D64: stands for filing and answering; a watch is a separate, fixed, approved outbound check]** **No autonomous agent.** One structured-extraction call at capture; for questions, a router in code, then a bounded read-only tool loop (4 turns, 6 calls), then plain search. The model never writes to the database or schedules anything | An agent that manages the notes; a multi-agent pipeline; sending the top notes and asking (first design); always using the model for questions | The capture task is the same every time and nobody reviews it; a form-filling call is testable and cannot do harm. Questions about readings and tasks are queries, which tools express and text search does not. |
| D44 | **[Amended by D70: still the first and only provider, now behind a provider-neutral seam]** **Claude Haiku 5.5 for both steps, structured outputs for extraction, strict tools for the loop, called through the prototype's own small HTTP client** | The Anthropic Java SDK; a larger model by default; hand-parsed JSON (the prototype) | Smallest capable tier at about $0.0003 a note. The SDK is the usual recommendation, but here it would add two large libraries for one endpoint and was never verified on Android; the existing seam already supports recorded-response tests. Revisit if the API surface used grows. |
| D45 | **The extraction call is given the word list, known subject and metric names, and open task titles, built only from non-private notes** | Sending the note alone; sending recent notes for context | Consistent names and closing-by-speaking need it. It widens what leaves the phone slightly, which PRIVACY.md states and Q20 asks the owner to accept. |
| D46 | **[Amended by D77 and D82, 2026-11-12: voice notes keep their audio and are written out by a bundled engine; the phone's recogniser stays as the "quick note, no recording" route]** **Keep Android's on-device recogniser; no bundled speech model; no audio is ever stored** | Recording the audio ourselves and bundling sherpa-onnx (D7, D8); keeping failed audio encrypted for retry (D9) | The prototype's recogniser transcribed correctly with no download. The bundled engine was chosen for sameness across three makers' phones, which is no longer the goal. Cost: a failed recognition cannot be retried. Reopen if R12's spike fails badly. |
| D47 | **[Superseded by D56, 2026-11-11: understanding first, hardening as one block after the usefulness check]** **Build order: data model and migration; app gate and encryption; extraction pipeline; hosted call and measurement; tasks; reminders; readings; asking; attention list; backup** | Encryption first; the hosted call first | The schema is what everything else stands on, and migrating while the database is still readable lets the migration be checked with `peek.py`. The gate and encryption come next, before the model starts receiving unfiltered speech in daily use. |
| D48 | **[Amended by D60: "at most 2 a day" is now 2 scheduled plus 2 event, 4 in all, decided in one place]** **Nudging is digest-first: at most 2 notifications a day, none on empty days, quiet hours, back-off after 3 ignores, the daily digest stops itself after 5 unopened days and says so** | A notification per task; persistent re-nagging until done; the first design's budget of 3 | His words were "You have things you wanted to do", which is a digest. Reminder apps that never stop get uninstalled. |
| D49 | **An attention list holds what the app was unsure about; it never blocks, never notifies by itself, and is optional reading** | Asking him to confirm each note; hiding uncertainty | He asked for no verification. Doubts still need somewhere to go. |
| D50 | **Full-text search through Room's FTS4 support, ranked in code** | FTS5 by raw SQL (first design); in-memory keyword scoring (prototype) | First-class in Room, so simpler for the builder; enough at a few thousand short documents. FTS5 is a contained change if ranking proves weak. |
| D51 | **[Amended by D57: now twenty-three cards; two of the twelve were split]** **The thirty first-design cards are archived and replaced by twelve thicker ones** | Editing the old cards in place | They were sized and ordered for a three-household rollout with spikes on three phones. `docs/cards/ARCHIVE.md` says what happened to each. |
| D52 | **An on-device model is a spike (card 12), not a plan** | Designing around Gemini Nano now; bundling an open model | Beta, foreground-only, quality unknown. Half a day settles whether it can serve private notes. |
| D53 | **Real notes used for measurement stay out of the repository** (a git-ignored folder on the owner's PC); only rewritten, harmless sentences join the seed set | Committing a sample of real notes | The repository may be shown to others. |
| D54 | **Questions sent to the model carry note ages in words ("9 days ago"), never timestamps** | Sending dates; sending nothing about time | Answers need to say how old a note is; the phone's clock still does not leave. | D55 | **The first-design documents are kept as dated copies under `docs/archive/`** | Overwriting them | The three-phone analysis is still the reference when the family rollout resumes. |
