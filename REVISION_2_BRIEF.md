## New material to integrate (the owner's own thoughts, paraphrased faithfully)

### 1. Trips
- Idea: when the app realises the user is leaving home it could ask "Track this trip? Yes/No." Example trip: Costco, then Ross, then Total Wine. At Costco: "I just picked up a bag of nuts, some Alaskan Amber and some Tide; the Tide is on sale for $24.99." Later: "Just bought some jeans at Ross." Later: "I found this wine for $4.97 per bottle, I took a picture of it, can you make note of it?" Then home.
- The point of tracking a trip is to answer **"when was the last time I went out?"** plus extras: who drove, which car, and little nags: "Remember your wallet and keys!", personalised from what the app knows ("remember your purse, keys and reading glasses").
- Owner's refinement: a trip can be **built from the user's own notes**: a note taken at Costco already carries when and where and the user's details, likewise Ross and Total Wine, so background location is **not required** for the core feature; automatic detection is a bonus for trips with no notes. Some features (automatic trip recognition) do need more access and can only be partly supported without it; say what degrades.
- Design: a **trip** record (start, end, places, vehicle, driver, the notes made during it, optional summary), prices as readings ("what was the Tide price last time?"), a **leaving checklist** that can depend on the destination or the vehicle (membership card and open "buy at Costco" tasks; the charger adapter in the Tesla), and departure/arrival triggers. Evaluate the cheaper departure/arrival signals as well as geofence exit: disconnect from the home Wi-Fi, connection to a car's Bluetooth (which also says which car), a manual "start a trip" (voice command or notification button), Android activity-recognition transitions. State permissions, battery, reliability on Android 17 and Samsung's battery manager, and false-trigger risks for each. Respect the existing notification budget and de-escalation rules (RISKS R14): nags are where this goes wrong.

### 2. Photos and screenshots
- A photo "made note of" in a note is stored **separately** from the text, linked to the note, only once it has been tagged as important to a note, at the **minimum legible resolution** that keeps storage small. Local only by default.
- Screenshot scenario: the user is in Instagram, sees a band they love, takes a screengrab; the app offers "include your recent screengrab in a note?"; if yes, the user voice-annotates what matters: "I love Saves the Day; when they tour in Phoenix again I'd want to go, so alert me if they're in town."
- Evaluate how to detect or receive the screenshot with the least permission: watching the media library (broad photo access or partial access on Android 14+) versus a **"Share to Stash"** target from the screenshot preview or the share sheet (no extra permission; the user chooses each time). Recommend. Also evaluate on-device text recognition (e.g. ML Kit text recognition, on-device) so a price tag or poster is searchable without sending the picture anywhere; image downscaling and format choices; encryption of image files; deletion with the note; and whether sending images to a hosted model is ever wise (default off; per-image consent; faces and other people's information).

### 3. Scheduled "watches" (read-only web searches on the user's behalf)
- A note can imply a recurring check: "the first Monday of every month, search for Saves the Day in Phoenix and the surrounding area, and alert me when it is true."
- This is a **different privacy class**: outbound queries reveal interests and location, and something must run while the phone is idle. Design a **Watches** list: each watch shown in one place with exactly what is sent and how often, cancellable, with caps on frequency and cost, read-only, alerting only on a real match, with a plan for false positives and dead sources. Evaluate where it can run (on the phone with WorkManager and a search API or a model with a web-search tool; versus anything server-side, which would break "no server of ours"), which services, cost, what a hosted model sees, and how to keep the query minimal. Sequence it **last**.

### 4. Support and diagnostics for a possible product (design now, build later)
- A customer may get an unexpected answer after making notes and screengrabs. A product would need support, and the developer must be able to find root causes **without clear access to the customer's data**.
- The owner proposed a dictionary mapping nouns and verbs to GUIDs, with the database holding only GUIDs and friendly names shown to the user, so records are unique but not identifiable. Evaluate this honestly. Starting position to test or overturn: pseudonymization is the right instinct but wrong **place** (the extraction model needs real words; a dictionary on the same phone protects little; tokens are not anonymity because dates, prices, counts and locations re-identify; privacy law generally still treats pseudonymized data as personal data; it would complicate search). Better: **(a)** a "Why this answer?" view stored from a local **answer trace** (what the router chose, which records and quotes matched, tool calls, what the model was asked), so the user can often find the cause themselves with nothing leaving the phone; **(b)** a user-initiated **diagnostic report** built at share time, with **fresh random per-report tokens** ("Place 1", "Item 2"), structure, kinds, counts, confidence, timings and error codes, never note text by default, previewed by the user and sent as a file the user chooses where to send; the decode table stays on the phone so the user can decode a token if support asks and chooses to; **(c)** for hard cases, the user selects a specific note and sends it encrypted to support with an expiry, after a preview; **(d)** user-substituted reproduction ("replace Costco with a made-up store"). Keep logs to events and codes, never note content, from now on. State what it costs in the data model now (the answer trace) versus later.

### 5. Storage decision (the owner is worried about being blasé now and overhauling the backend later)
Write a short **storage decision record** comparing: plain Room (today); full-database encryption (SQLCipher via Room's open-helper support, key in the hardware-backed Android Keystore); field-level encryption; and the **sealed inbox** (a note captured while locked is encrypted to a public key and parked; the private key is usable only after the user authenticates; making "reading needs unlock" a cryptographic fact rather than app logic); plus end-to-end encrypted backup, and if ever needed, end-to-end encrypted sync. For each: security gained, speed cost on search and answers, migration cost from the prototype, and when to choose it. Separate **decisions to make now because they are expensive to change later** from **things that can be added later cheaply**. My working list of the former: all data access through one layer; permanent random IDs (UUIDs) on every record for later backup/merge/sync; raw text kept apart from derived data; versioned schema with tested migrations from day one; a plain open export format. Challenge this list: what else belongs on it (image files, answer traces, watch definitions, trip records, deletion semantics, key rotation, schema for model-extractor versions)? Verify, or say how to verify, current SQLCipher/Room compatibility, performance on Android 17, licensing, and APK size. Give the owner the **preferred, most secure solution that still allows convenient, speedy access** and say what you would do and when.
